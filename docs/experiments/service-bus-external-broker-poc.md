# Service Bus external broker PoC

Experimental branch based on upstream commit `2a8a555e86f21adf5cc75fda9218dfdd83b33d31`.
This is a feasibility prototype, not a release-ready integration.

## Changes

- Preserve exhausted delivery counts and `MaxDeliveryCountExceeded` when messages enter the DLQ.
- Allow an orchestrator to start Artemis and let floci-az connect without controlling Docker.
- Keep the external broker running when floci-az stops. Accept only the configured namespace.

The DLQ fix extends the existing Maven patch mechanism to `QueueImpl` in
`artemis-server`. An Artemis upgrade therefore needs to revalidate this additional patch.

## Checked locally

- 210 Service Bus module tests passed.
- Four real Java SDK scenarios passed: exhausted deliveries, send/complete, abandon,
  and explicit dead-letter. The exhausted-count assertion failed before the fix.
- Five Python SDK protocol cases passed, including new exhausted-delivery cases
  for topic subscriptions with and without sessions. The suite also passed after
  restarting floci-az.
- Two native ARM64 containers ran on an internal Docker network, without a Docker
  socket mount or privileged mode. Stopping floci-az left the broker running.

Before the fix, Python peek after ten abandons reported count `0` and no reason.
After the fix it reported count `10` and `MaxDeliveryCountExceeded`; receiving the
DLQ message and processing the next normal message also worked.

## Testing

Use JDK 25 for the emulator build:

```sh
./mvnw test '-Dtest=*ServiceBus*Test,ArtemisPatchVersionsTest'
./mvnw package -DskipTests
```

For the SDK tests, start the emulator with a prepared broker, then set
`FLOCI_AZ_ENDPOINT`, `SERVICEBUS_HOST`, `SERVICEBUS_NAMESPACE`, and the appropriate
broker port. Python needs `azure-servicebus==7.15.0`, as pinned by its suite.

```sh
python -m pytest -q compatibility-tests/sdk-test-python/tests/test_servicebus.py
./mvnw -f compatibility-tests/sdk-test-java/pom.xml test \
  -Dtest=ServiceBusCompatibilityTest#maxDeliveryCountDeadLettersAfterEntityLimit
```

Python uses `SERVICEBUS_AMQP_PORT`; Java uses `SERVICEBUS_AMQPS_PORT` and trusts
the certificate returned by the namespace API. See the
[external broker settings](../services/service-bus.md#external-broker-prototype).

## Still manual or unverified

- Preparing a broker image is not automated. The local experiment reused the XML,
  management configuration and TLS bundle generated by a managed broker, and
  installed all patch jars from the same Maven build. Stock Artemis alone is not enough.
- Do not commit generated private keys or copy old patch jars into a newer broker image.
- The consuming application's full end-to-end suite has not been run. These SDK
  exercises do not prove its archive, downstream delivery or failure-recovery flows.
- No Linux CI or long-duration stability run was done.
- Broker version validation, bad certificates and unavailable-broker startup need
  more coverage before treating this as a supported external-broker mode.
- Java SDK peek hung against unmodified upstream. The Java regression uses receive;
  Python covers both peek and receive. No Java-peek workaround is included.
